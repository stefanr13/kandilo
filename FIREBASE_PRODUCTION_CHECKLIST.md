# Kandilo Firebase Production Checklist

For the current parish and pay-at-pickup release, also follow [Production stabilization](docs/PRODUCTION_STABILIZATION.md). Its deployment ordering, new event/push callables, Saints migration, and device checks extend this checklist's Stripe/receipt scope.

Use this when preparing `kandilo-2f7a9` for production deployment and physical-device testing. Do not commit local secrets, native Firebase config files, signing files, or generated native web assets.

## 1. Required Local Files

- `.env.local` at the repo root with the public Vite/Firebase values from Firebase Console, including `VITE_FIREBASE_STORAGE_BUCKET=kandilo-2f7a9.firebasestorage.app` so retained receipt PDF smoke checks read the same production bucket used by Functions.
- `functions/.env.kandilo-2f7a9` with `APP_URL=https://app.kandilo.org`.
- `ios/App/App/GoogleService-Info.plist` for local iOS builds.
- `android/app/google-services.json` for local Android builds.

These files are intentionally gitignored where they contain environment-specific configuration.

For local emulators, use ignored `functions/.env.local` with `APP_URL=http://localhost:3000`. Firebase loads it after the project-specific file only in emulator mode, so local email and checkout links keep pointing to localhost.

## 2. Firebase Console Setup

Confirm these Firebase services are enabled:

- Authentication: Email/password, Google, anonymous.
- Firestore.
- Firebase Storage.
- Cloud Functions.
- Firebase Hosting for `app.kandilo.org`.
- Firebase Cloud Messaging.
- App Check.

Authentication authorized domains should include `app.kandilo.org`, the Firebase default auth domain, and localhost for development.

If Firebase CLI reports that Storage has not been set up, open Firebase Console -> Storage for `kandilo-2f7a9`, click "Get Started", choose the production bucket location, then deploy `storage.rules`.

## 3. Secrets And Environment

Set Cloud Functions secrets in Firebase Secret Manager:

```bash
npx --no-install firebase functions:secrets:set GEMINI_API_KEY --project kandilo-2f7a9
npm run configure:receipt-secrets -- --set RESEND_API_KEY --confirm-project kandilo-2f7a9
npm run configure:receipt-secrets -- --set STRIPE_SECRET_KEY --confirm-project kandilo-2f7a9
npm run configure:receipt-secrets -- --set STRIPE_WEBHOOK_SECRET --confirm-project kandilo-2f7a9
```

Use `npm run configure:receipt-secrets` for the no-network plan, or `npm run configure:receipt-secrets -- --set-all --confirm-project kandilo-2f7a9` to set the three receipt-path production secrets in sequence. The helper checks `.firebaserc`, uses the repo-pinned Firebase CLI, and never reads or prints secret values.

`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` can stay on test-mode values until Stripe is ready for production.

## 4. Deploy Rules, Indexes, Functions, Hosting

From the repo root:

```bash
npm run check
npm run check:stripe-production
npm run build
npm --prefix functions run build

npx --no-install firebase deploy --only firestore:rules,firestore:indexes,storage --project kandilo-2f7a9
npx --no-install firebase deploy --only functions --project kandilo-2f7a9
npx --no-install firebase deploy --only hosting --project kandilo-2f7a9
npm run check:firebase-live
```

### Public Coming-Soon Gate And Full-App Preview QA

When the public app should stay unpublished, deploy the gated holding-page build
to the live Firebase Hosting site:

```bash
npm run build:coming-soon
npx --no-install firebase deploy --only hosting --project kandilo-2f7a9
```

This keeps both `https://app.kandilo.org` and
`https://kandilo-2f7a9.web.app` on the "Kandilo is preparing for launch"
screen. The gate is controlled by `VITE_COMING_SOON=true`; the normal app shell
is not mounted in that build.

To test the full production web app without replacing the public holding page,
build normally and deploy the current `dist` output to a Firebase Hosting preview
channel:

```bash
npm run build
npx --no-install firebase hosting:channel:deploy full-app-test --project kandilo-2f7a9 --expires 30d
```

Use the printed channel URL for production-like QA. For example, the current
full-app test channel is:

```text
https://kandilo-2f7a9--full-app-test-62rxs576.web.app
```

Do not deploy the normal `npm run build` output to live Hosting while the public
app is meant to remain unpublished. After publishing or refreshing a preview
channel, rebuild and redeploy `build:coming-soon` to live Hosting if there is
any uncertainty about which bundle is currently on the public channel.

When the app is ready to publish publicly, remove the gate by deploying a normal
production build to live Hosting:

```bash
npm run build
npx --no-install firebase deploy --only hosting --project kandilo-2f7a9
```

For the Stripe/tax receipt release surface specifically, prefer the guarded helper so Functions, Firestore rules, Firestore indexes, Storage rules, and the hosted portal UI are deployed together after the full local QA gate:

```bash
npm run deploy:tax-receipts:plan
npm run deploy:tax-receipts -- --confirm-project kandilo-2f7a9
```

The plan command is read-only and reports whether the current Xcode project and Android release-signing configuration can derive final native app-link identifiers locally. The deploy command refuses to run unless the live project is explicitly confirmed and the local runtime is Node 22, then runs `npm run check:stripe-production -- --strict-native-links`, `npm run lint`, `npm run test:qa`, `npm run build`, `npm run audit:tax-receipts -- --fail-on-repairs`, deploys `functions,firestore:rules,firestore:indexes,storage,hosting` with the repo-pinned Firebase CLI from `devDependencies`, and finishes with `npm run check:firebase-live -- --strict-native-links` plus `npm run audit:tax-receipts -- --fail-on-repairs`. The explicit build keeps the hosted donor/church receipt portal fresh even if other QA scripts change later. The pre-deploy audit prevents known unsafe legacy receipt visibility metadata from going live with the new receipt manager surface; the post-deploy audit confirms the data gate is still clean after release.

After deploy, `npm run check:firebase-live` is read-only and first confirms the local `dist` build is current with frontend source inputs, then uses the Firebase CLI, Cloud Scheduler API, Firebase Rules API, and public Hosting fetches to confirm the deployed Node 22 Functions are active, the scheduled annual receipt job is enabled with the expected `every 24 hours` / `Etc/UTC` cadence and no automatic retries, legacy-safe giving shims are active, exact Stripe/Resend secret bindings are present on deployed Functions, no unexpected remote-only Stripe/payment/checkout/giving/receipt Functions remain deployed, enabled Secret Manager metadata for Stripe/Resend secrets, Firestore indexes, Firestore rules, Storage rules, hosted `https://app.kandilo.org` security headers, hosted build asset references/files, and hosted `.well-known` universal/app-link files include the current Stripe/tax receipt production surface; it continues checking the hosted native-link files even when the deployed SPA asset references are stale so separate Stripe/native return blockers are not hidden. It should pass before live receipt testing.

## 5. Stripe Setup

The app is wired for hosted Stripe Checkout through Cloud Functions. By default, donations settle to the configured platform Stripe account. SuperAdmins can also create a U.S. or Canadian Stripe Accounts v2 recipient connected account with Express dashboard access for a church from Mission Control, or paste an existing `acct_...` ID when the account was created in Stripe. The connected account ID is stored only in backend-only `churchPaymentSettings/{churchId}`. In-app account creation stores the account with routing disabled and `stripeConnectAccountApi='v2'`, so priests and treasurers can finish Stripe-hosted v2 onboarding before a SuperAdmin enables parish routing. When pasting an existing account, Mission Control defaults the account API selector to Accounts v2 recipient and should only use the legacy v1 account option for a pre-existing legacy account. SuperAdmin save preserves the stored account API version, honors an explicit v1/v2 selection for pasted accounts, and verifies the connected account is ready with the configured Stripe key before enabling routing; Checkout uses destination-charge routing (`payment_intent_data.transfer_data.destination`) only after Stripe reports that the connected account can receive transfers, has no currently due or past-due requirements, and, for legacy-compatible pasted accounts, can charge, pay out, and has submitted details. Priests and treasurers can see a coarse configured/routing-enabled connected-account setup status and can open a Stripe-hosted onboarding link from the receipt manager only after that setup status confirms a connected account is configured, without seeing the account ID; return and refresh links are bound to a client-generated session state token before the receipt manager shows a Stripe return notice. Initial production donations are pinned to card Checkout so donation completion and tax receipt readiness stay immediate; do not enable delayed payment methods until the webhook and receipt states explicitly handle delayed settlement.

## 8. Universal Links

The repo includes the well-known files, entitlements, custom URL scheme, and URL handling. Keep the checked-in hosted files inert until final store identifiers are available; do not publish debug app-link trust files to production Hosting. Final store builds still need production identifiers:

```bash
npm run configure:native-links -- --apple-team-id TEAMID1234 --android-sha256 AA:BB:...:99
# Or, when Xcode has the Apple team selected and android/keystore.properties or KANDILO_UPLOAD_* points at the release signing key:
npm run configure:native-links -- --apple-from-xcode-project --android-from-release-keystore
# Or, when only Android can be derived from local release signing config:
npm run configure:native-links -- --apple-team-id TEAMID1234 --android-from-release-keystore
```

Use the real 10-character Apple Team ID for `com.kandilo.app` and the full 32-byte Android release signing SHA-256 fingerprint. The helper rewrites both hosted well-known files, refuses the known Android debug keystore fingerprint, supports repeating `--android-sha256` if there are multiple release signing certificates, can derive the Apple Team ID from the iOS Xcode project `DEVELOPMENT_TEAM`, and can derive the Android fingerprint from the same release keystore config used by Gradle without putting keystore passwords in the `keytool` command arguments. `npm run check:stripe-production` warns until both files are final; the guarded deploy helper treats this as deploy-blocking through `--strict-native-links`.

Deploy hosting after updating these files. This is needed for HTTPS invite links and payment return links to open the native app reliably.
